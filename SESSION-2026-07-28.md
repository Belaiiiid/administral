## 1. Lancer MonParcours en local

**Demande initiale** : faire tourner l'app en local pour voir si ça marche.

- Frontend (Vite/React) : `npm install` puis `npm run dev` → http://localhost:5173
  (le proxy `/api` de `vite.config.ts` redirige vers le backend `:8000`).
- Découverte : un ancien process backend tournait déjà sur le port 8000,
  mais avec du **code obsolète** (routes manquantes : `agent`, `citizen`,
  `contestation`...). Arrêté et remplacé.
- Backend (FastAPI) : besoin de PostgreSQL, absent de la machine.
  - Installation de **PostgreSQL 17** via `winget` — le téléchoargement
    depuis `get.enterprisedb.com` renvoyait un 403 CloudFront avec les
    en-têtes par défaut de `curl`/`winget` ; résolu avec un User-Agent de
    navigateur (pas un vrai blocage réseau, juste une protection anti-bot).
  - Base `monparcours` créée, migrations Alembic appliquées.
  - Deux incompatibilités **Python 3.14** (seul interpréteur present sur la
    machine) découvertes et corrigées par bump de version :
    `psycopg2-binary` 2.9.10 → 2.9.12, `SQLAlchemy` 2.0.36 → 2.0.51.
- Chargement des données de test : `python -m scripts.load_test_data` —
  crée 3 comptes de démo et 3 dossiers (dont un validé + contesté) :
  - `citoyen@monparcours.fr` / `Citoyen1234`
  - `agent@monparcours.fr` / `Agent1234`
  - `admin@monparcours.fr` / `Admin1234`

**Résultat** : app fonctionnelle en local, backend `:8000`, frontend `:5173`.

## 3. Pont vocal WhatsApp ↔ chatbot (fonctionnalité majeure)

**Besoin exprimé** : un citoyen pose une question vocale sur WhatsApp,
reçoit une réponse vocale, générée par le vrai assistant RAG du backend —
mais **jamais** sur son dossier personnel (seulement questions générales
APL), et **tout en local/souverain** (pas d'API cloud de reconnaissance ou
de synthèse vocale), cohérent avec la doctrine RGPD déjà posée par le bot.

Passage en mode plan (exploration via agents dédiés, conception validée par
un agent de revue) avant implémentation. Plan approuvé :

- **STT** : `faster-whisper` (modèle `small`, français, local, CPU).
- **TTS** : `Piper` (voix `fr_FR-siwis-medium`, local).
- **Conversion** : `ffmpeg` (WAV → OGG/Opus, requis par WhatsApp pour
  qu'un message s'affiche en bulle "note vocale" plutôt qu'en pièce jointe).
- **Porte de sécurité** : `handlers.is_sensitive_for_voice` filtre les mots-clés
  document/dossier *avant* tout appel au backend — ces questions reçoivent
  la redirection texte statique existante, jamais une réponse vocale.
- Risque anticipé (incompatibilité Python 3.14) : **non avéré** — `ctranslate2`
  et `onnxruntime` avaient déjà des wheels précompilées pour cette version.

**Fichiers ajoutés** : `app/stt.py`, `app/tts.py`, `app/chatbot_client.py`,
`app/voice_pipeline.py` (orchestration avec repli systématique en texte à
chaque étape qui peut échouer). **Fichiers modifiés** : `handlers.py`,
`whatsapp_client.py`, `config.py`, `main.py`. **12 nouveaux tests
unitaires** (27 au total, tous passent). Pipeline validé en local de bout
en bout (texte → Piper → ffmpeg → faster-whisper → texte identique).

**Committé** (`99014aa`), puis **poussé** sur GitHub.

## 4. Vérification en conditions réelles (tunnel ngrok)

Pour que Meta puisse livrer un vrai webhook vers le service local (port
8001), il fallait un tunnel public.

- **Blocage réseau** : le wifi de l'endroit où le PC était connecté
  (`Talan_Gst`, pas littéralement "HEC" malgré le nom du dossier) filtre
  `dashboard.ngrok.com` via un proxy Fortinet — confirmé technique, pas
  contourné (bascule sur un partage de connexion téléphone à la place).
- **Faux positif antivirus** : Windows Defender a mis en quarantaine
  `ngrok.exe` (`Trojan:Win32/Kepavll!rfn`, sévérité 5) — sur **deux
  binaires différents** issus de sources officielles différentes, avec le
  même identifiant de menace. Signal fort de faux positif heuristique
  (comportement de tunnel = pattern générique de trojan pour les
  antivirus). Résolu par une **exclusion Defender ciblée** sur un seul
  dossier, ajoutée par l'utilisateur (pas de désactivation générale).
- **Tunnel opérationnel**, webhook configuré côté Meta (`messages` bien
  abonné). Le **webhook de test** envoyé depuis le dashboard Meta est bien
  arrivé (preuve que toute la chaîne fonctionne : tunnel → FastAPI →
  routage → gestion d'erreur).
- **Un vrai message vocal n'est jamais arrivé** : confirmé qu'il s'agit
  d'une restriction Meta documentée — une app non publiée ne reçoit que
  les webhooks de test du dashboard, jamais de vraies données, même d'un
  testeur vérifié. Décision de **s'arrêter là** plutôt que de publier
  l'app (implique politique de confidentialité etc., décision à part).

## 6. Bug trouvé et corrigé : dossier du chatbot

En explorant le code pour lister d'autres améliorations possibles, découverte
d'un vrai bug : `backend/app/modules/chatbot/service.py::_answer_dossier`
répondait **toujours** sur un dossier de démo fixe (`TEST-DOSSIER-0001`),
peu importe quel citoyen posait la question "où en est mon dossier ?".

**Correction** : résolution du vrai `Citizen` de l'utilisateur connecté
(via `user_id`, même règle que `contestation/service.py`), puis son vrai
`Case` (ou son dossier personnalisé s'il n'a pas encore soumis). Un appel
anonyme reçoit une invitation à se connecter plutôt que le dossier de
quelqu'un d'autre.

Vérifié en conditions réelles : le compte citoyen de démo reçoit
maintenant sa vraie réponse (`2026-APL-0417`, validé). Suite de tests
backend relancée (101 passent, 8 échecs pré-existants et sans rapport dans
`test_profilage.py`, un souci asyncio/Python 3.14 séparé).

**Non committé** : ce dépôt MonParcours n'a aucune identité git configurée
sur cette machine, et il s'agit d'un projet d'équipe (remote
`Belaiiiid/MonParcours`, commits antérieurs d'autres personnes). Le choix a
été fait de ne pas configurer git sans confirmation, et l'utilisateur a
préféré régler ça lui-même avec son équipe plus tard.
